# T9：审核证据与审核精度

日期：2026-10-15
状态：草案，待确认
前置：`2026-10-15-audit-launch-t8.md`（T8 已完成，分支 `feat/audit-projects`）

## 0. 现状调研结论

### 0.1 证据在收录时被丢弃

- H5 原版 `results.json` 的每个会场带 `check_evidence`：截图文件、sha256、`crop_px`、`marks[].bbox_px`、说明，并区分 localized / context / missing。v2 收录时只保留 observed / reason 两段文字，证据固定写成 `{"kind":"h5_report","image_ids":[]}`（`audit_workspace.py:227`）。
- App 的 `inspection_json.checks[]` 有 `bbox`（像素，`inspection.py:106`），但 `aggregate_app_findings` 只保留 image_ids，没有保留框。
- 前端 `AuditTargetDetail` 和 `AuditPageLifeline` 没有任何证据组件。
- 这是 v2 spec 第 18 行刻意划出的范围（“截图在后续版本接入”）。结果是平台版的可验证性比原版报告差：只有文字，无法判断模型是否看错。

### 0.2 原版审核的精度瓶颈（408 会场 v5 全量数据）

| 发现 | 数据 | 含义 |
| --- | --- | --- |
| **一半会场根本没采到目标页** | 206/408 为 page_error；其中 179 个是“活动迷路了”兜底页，2 个要求登录，2 个活动已过期 | 这些会场仍各调用了一次 GPT-5.5（单次约 80 秒），由模型告诉我们“这不是目标页”。采集端完全可以先判断出来。 |
| 有效会场里的待确认集中在少数规则 | OV-009 87、OV-001 69、OV-004 46、OV-005/023 40、OV-003 30、OV-010 27、OV-015 27 | 主要原因：找不到分类 Tab（67）、首屏商品区不完整或截图已滚动（36）、出现楼层异常提示。都是“采集画面不够好”或“定位不到元素”，而不是规则本身难判断。 |
| 几乎所有判定都只靠一次模型调用 | 有效 checks 中 2,424 条 method=`h5_user_policy_v2`（纯模型），只有 94 条用了实时 DOM 测量（OV-009） | 每个会场只调用一次模型，没有复核。 |
| 像素测量的位置由模型决定 | OV-010 的取样框 `localization_method=vlm_normalized_roi` | 模型框偏了，像素测量就测错了地方，而且结果看起来像精确测量。 |
| 证据框大多来自模型 | 2,351 个 localized 框来自模型坐标，79 个来自 DOM | 框是模型“说”的位置，没有经过独立核对。 |
| 没有准确率数据 | 没有人工判定记录 | 现在无法回答“OV-017 的不符合有几成是误报”。所有精度改进都无从衡量。 |

结论：T9 不只是把截图接回来。更大的收益在于：
1. 在采集端拦下无效页面；
2. 能用 DOM 或像素确定的规则，不再交给模型猜；
3. 建立人工复核与准确率度量，让后续的每次改进都能被量化。

## 1. 目标与边界

做：

- **T9a 证据可见**：H5 与 App 的截图、裁切、框选、测量值都能在平台中查看，并比原版多交代三件事：证据来源（DOM / 像素 / 模型）、是否已核对、整屏上下文。
- **T9b 采集闸门**：采集后先做确定性检查，识别无效页面并给出原因代码，无效页面不调用模型。
- **T9c 确定性测量**：采集时保存 DOM 快照。可测量的规则改为以 DOM 或像素为主、模型为辅，两者冲突时判为待确认并同时展示双方依据。
- **T9d 人工复核与准确率**：逐条 finding 记录人工判定；按规则统计误报率和漏报率；提供黄金集回归脚本，每次修改提示词或规范前后都能比较。
- **T9e 模型放大复核**：仅针对模型判为不符合或因“看不清”而待确认的条目，用证据区域的放大裁切再问一次单规则问题；两次结论不一致时判为待确认。

不做：

- 跨轮像素差异对比（上线前后同页的变化区域）：列入 §8 后续候选。
- Android UI 层级（uiautomator dump）作为 App 端的确定性来源：列入 §8。
- 规范 PDF 解析、新权限角色。
- 改写既有规则的判定标准。T9 改的是“怎么测”，不改“标准是什么”。

## 2. 数据模型

### 2.1 Finding 证据结构 v2（存放在 `findings_json`，不改表）

```json
"evidence": {
  "kind": "h5_report | app_images",
  "image_ids": [],
  "items": [{
    "asset": "<sha256>", "screen": 1, "image_size": [390, 844],
    "crop_px": [0, 312, 390, 500],
    "marks": [{"kind": "rect", "bbox_px": [0, 336, 390, 476], "label": "...", "source": "dom|pixel|model"}],
    "role": "localized | context",
    "label": "原截图 1 · ..."
  }],
  "measurements": [{"id": "...", "kind": "distance|color|count|text_length", "value": 12, "unit": "px",
                     "expected": "7–9px", "verdict": "fail", "source": "dom|pixel", "verified": true}],
  "state": "localized | context | missing | not_attached"
},
"method": "model | dom | pixel | hybrid",
"model_status": "fail",
"zoom_check": {"status": "agree | disagree | skipped", "reason": "..."}
```

- 旧数据没有 `items`，前端按 `not_attached` 显示。`image_ids` 保留，向后兼容。
- `model_status` 记录模型的原始结论；`status` 为最终结论。由 DOM 或像素改判时，两者都保留。

### 2.2 新表 `audit_evidence_assets`

| 字段 | 说明 |
| --- | --- |
| `sha256` PK | 内容寻址 |
| `mime`、`width`、`height`、`bytes` | |
| `storage_path` | `data/audit-evidence/<sha前2位>/<sha256>.<ext>`，相对路径 |
| `created_at`、`first_run_id` | |

写入前校验文件 sha256 是否与报告记录一致，不一致时拒绝写入，并在 finding 上标记 `evidence_integrity_error`。同一张图只存一份。App 截图已经在 OSS 或 `images` 表里，不再复制，通过 `image_id` 引用。

### 2.3 新表 `audit_finding_reviews`（T9d）

| 字段 | 说明 |
| --- | --- |
| `id`、`target_id` FK、`rule_id` | |
| `verdict` | `confirmed` 确认问题 / `false_positive` 误报 / `false_negative` 漏报 / `exception` 接受例外 / `recapture` 需重采 |
| `corrected_status` | 人工认定的状态（pass/fail/not_applicable），可为空 |
| `note`、`created_by`、`created_at` | |

- 只追加，不修改；以同一 target + rule 的最新一条为准。
- 项目指标（闭环率、规则流向）改用“有效状态”：有人工判定时以人工为准，否则用 `status`。

## 3. 各子任务

### 3.1 T9a 证据可见

**收录**
- `parse_h5_results` 读取 `check_evidence`，转换为 v2 结构。图片从 run 目录（H5 执行器）或上传的 zip（手动导入）写入 asset 存储。
- 手动导入新增“附带证据包（zip）”选项；只传 `results.json` 时，证据为 `not_attached`。
- `aggregate_app_findings` 保留每张截图的 `bbox`，作为 `marks`（source=model）。

**API**
- `GET /api/audit-evidence/{sha256}`：需登录；只回传 `audit_evidence_assets` 中登记过的文件；设置强缓存（内容寻址，不会变）。
- App 图片沿用既有的图片接口。

**界面**（每条 finding 一张卡片）
- 状态、规则、observed / reason（保留现有内容）。
- 证据条：局部裁切图加框线；点击后打开整屏查看器，可在两屏之间切换，框线与裁切保持一致。
- 来源徽章：`DOM 测量` / `像素测量` / `模型判断`。模型框标注“模型定位，未核对”。
- 有测量值时显示“实测 12px · 规范 7–9px”。
- 有改判时显示“模型：不符合 → 测量：符合”。
- 没有局部定位：显示整屏图，并标注“暂无局部定位”。
- 未附证据：显示“证据未随附”，并提供“补传证据包”入口。
- 页面生命线（`AuditPageLifeline`）的选中详情使用同一组件；上线前和上线后的证据可以并排对照。

**补数据**
- `scripts/backfill_audit_evidence.py --run <id> --source <zip或目录>`：为已收录的 run 补回证据。预演模式只输出匹配统计。按会场 ID 与 sha256 匹配，不匹配的不写入。

### 3.2 T9b 采集闸门

在 `capture_venues.mjs` 截图后，于同一页面执行确定性检查，结果写入 `capture.json.gate`：

| 原因代码 | 判定依据 |
| --- | --- |
| `venue_lost` | 页面文字含“活动迷路了”，或发生重定向且落地页不是目标 |
| `login_required` | 出现登录页或登录弹窗 |
| `expired` | “已过期 / 已结束的活动，暂不支持预览” |
| `floor_error` | 出现“楼层异常”提示（不阻断，标为 `degraded`，相关规则直接判为待确认） |
| `not_ready` | 骨架屏或 loading 超时，首屏图片未加载完成 |

- 阻断类（前四项中除 floor_error 外）：不调用模型，target 记为 `capture_failed` 并附原因代码。
- H5 job 结束时汇总各原因的数量。若 `venue_lost` 占比 ≥30%，在 job 卡片上提示“可能是预览时间或预览链接失效”，并提供“仅重采失败会场”按钮。
- 文案匹配规则集中放在同一个配置里，附测试夹具（用 408 批次的截图与 DOM 文本）。
- **待查**：179 个“活动迷路”的根因（预览时间、链接时效、登录态）。T9b 先做到识别和统计，根因在真实验收时定位。

### 3.3 T9c 确定性测量（DOM 优先）

**采集**：截图同时保存 `dom-snapshot.json`，包含视口、滚动位置、可见元素的矩形、标签、class、`data-*`、截断文字、计算后的背景色与字体，以及图片 src。大小上限 2MB。DOM 坐标与截图像素的换算比例写入快照，并校验与截图尺寸一致。

**测量器**（`backend/app/services/h5_measurers.py`，纯函数，输入 DOM 快照与截图，输出 measurement）：

| 规则 | 现状 | T9c 做法 | 可行性 |
| --- | --- | --- | --- |
| OV-009 Tab 上方间距 | 已有 DOM 测量，但 87 个会场找不到 Tab | 改为通用定位：横向排列、等高、文字短的元素组，再加吸顶行为特征 | 高 |
| OV-010 feeds 背景白色 | 在模型框内取样像素 | 先在 DOM 中找出 feeds 容器的计算背景色，再在其矩形内、商品卡之外取样像素交叉验证 | 高 |
| OV-005/023 首屏完整商品数 | 模型数 | 在 DOM 中统计完全落在首屏视口内的商品卡（重复兄弟节点结构加价格文字特征） | 中，需先探测 |
| OV-001/002 楼层顺序 | 模型看图 | 如果通天塔楼层容器带有可识别的楼层或模块标识，就直接读 DOM 顺序 | **未知，需先探测** |
| OV-017 主标题字数 | 模型读字 | 标题多数是图片，DOM 读不到。改用本地 OCR（RapidOCR / onnxruntime，离线）交叉核对字数，与模型不一致时判为待确认 | 中 |
| OV-014/015/016/018 | 模型 | 不变，由 T9e 放大复核兜底 | — |

**合并规则**
- 测量结果 `verified=true`（元素语义已确认、坐标换算已校验）时，以测量为准，`method=dom|pixel`。
- 测量未核对，或与模型结论冲突：判为 `uncertain`，同时展示双方依据，不偷偷覆盖。
- 证据框优先采用 DOM 矩形；模型框只在没有 DOM 矩形时使用，并标注来源。

**先行探测（T9c-0，1 个工作单元）**：用 408 批次中 20 个有效会场的实时页面，确认三件事：楼层容器有无稳定标识、商品卡能否唯一识别、Tab 定位率能否提升。得出结论后再决定 OV-001/002、OV-005/023 是否进入 T9c；不可行的维持模型判定。

### 3.4 T9d 人工复核与准确率

- finding 卡片上提供五个判定按钮（§2.3），可附备注；支持键盘快捷键，便于逐条快速复核。
- 规则准确率面板（规范版本页的“规则质量”分页）：每条规则显示已复核数、误报率、漏报率、待确认率，并按方法（模型 / DOM / 像素）拆分。复核样本少于 10 条时标注“样本不足”。
- **黄金集**：把已复核的 target 导出成固定集（截图、DOM 快照、人工结论）。`scripts/eval_audit_rules.py --gold <集> --profile <规范版本>` 重跑审核并输出每条规则的精确率和召回率，可与上一次的结果比较。修改提示词、规则说明或测量器前后都要跑一次，结果写进 commit 说明。
- 被判为误报的条目，在下一次审核中作为该规则的反例提示（只取人工确认过的，每条规则最多 3 个），由规范版本开关控制，默认关闭。

### 3.5 T9e 模型放大复核

- 触发条件：`status=fail`，或 `uncertain` 且原因属于“看不清 / 不完整”；`method=dom|pixel` 且已核对的条目不触发。
- 做法：以证据框外扩 15% 裁切，放大到长边 1024，加上对应整屏的缩略图，只问这一条规则，要求输出结构化的结论和框。
- 结论一致：保留原结论，记录 `zoom_check=agree`；不一致：判为 `uncertain`，同时展示两次的理由。
- 以审核任务为单位开关，默认开启；在发起审核的弹窗中显示预估的额外调用次数。

| 顺序 | 任务 | 依赖 | 交付 |
| --- | --- | --- | --- |
| 1 | T9a-1 收录与存储：证据结构 v2、asset 表、证据 API、App 保留 bbox、补数据脚本 | — | 已有 run 补回证据 |

| 4 | T9d 人工复核与准确率面板、黄金集导出、评估脚本 | T9a | 用户复核约 30 个会场，建立首批黄金集 |

## 6. 风险

- **黄金集需要你投入时间**：约 30 个会场 × 13 条规则。复核界面以快为目标（键盘操作、默认停在下一条），预估 1–2 小时。
- 实时页面会变化：DOM 快照和截图必须在同一时刻采集，并记录时间；历史批次没有 DOM 快照，T9c 只对新采集的批次生效。
- 本地 OCR 引入新依赖（onnxruntime 约 50MB）：只在 OV-017 启用，可关闭。
- 放大复核增加模型成本：只对不符合和待确认的条目触发；按 408 批次估算，每个有效会场约多 1–3 次调用。
- 证据存储会增长：每个会场两屏约 400KB，408 个会场约 160MB；内容寻址可避免重采时重复存储。

## 7. 验收情境

1. 408 批次补回证据后，打开任一有效会场：每条有定位的规则都显示裁切和框线，点击可查看整屏；来源徽章正确。
2. 只导入 `results.json` 的 run：显示“证据未随附”，补传 zip 后显示正常。
3. sha256 不一致的图片不入库，finding 标注完整性错误。
4. App run：每条规则显示对应截图和模型框。
5. 闸门离线重放 408 批次：179 个迷路、2 个登录、2 个过期被正确分类，有效会场不被误拦；被拦会场不调用模型。
6. 复核：标记误报后，项目闭环率与规则流向按有效状态更新；规则质量面板计数正确；样本不足时有标注。
7. 评估脚本在黄金集上输出每条规则的精确率和召回率，两次运行可以比较。
8. 测量与模型冲突时判为待确认，界面同时显示双方依据。
9. 放大复核结论不一致时判为待确认，并显示两次的理由；关闭开关时不触发。

## 8. 后续候选（不在 T9）

- **跨轮视觉差异**：同一页面上线前和上线后两次采集做像素差异，标出变化区域。没有变化的区域沿用上次的人工结论，只重审变化部分，降低巡检成本。
- **App 端确定性来源**：AutoGLM 每次截图时同时 dump Android UI 层级，让 App 规则也能做元素级测量。
- **规则说明自动修订建议**：根据误报集中的规则，生成规则文字和示例图的修改建议，供人工确认后再生成新的规范版本。
