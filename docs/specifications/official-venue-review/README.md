当前批量H5审核使用 [用户口径第3版](h5-v3.md) / [规则配置](h5-v3.json)：保留23项，13项激活、10项未激活，OV-007本轮忽略。第2版及上一轮20案例结果保留。下文保留PDF提取版说明；用户修订与原文来源分开记录，历史报告不覆盖。

已逐页核对《官方会场审核规则与重点体验走查》9 页的正文和图示，提取 **23 个检查项、8 个走查环节、11 张规范参考图**。此处交付的是规范资产及实施步骤，尚未执行该会场的真机走查，也未将整个流程接入 Worker。

## 三种固定结构

以下顺序来自第 2 页图示：

| 框架 | 结构 |
| --- | --- |

| B：权益导购 | 顶部导航 → 主视觉 → 权益/优惠券 → 分类 Tab → 商品 feeds；底部导航固定显示。 |

新增互动、招商、拉新等楼层，只能放置于 feeds 上方或以模块形式融入 feeds 内部。这个位置规则不能代替组件允许范围的审核。模板无法满足业务需求时，原文允许经过业务和设计评估后沟通加白；走查应保留具体审批及其适用范围。

权益组件允许样式为：平铺权益券包有标题、平铺权益券包无标题、权益平铺（优惠券 + 商品券）。导购魔方允许样式为：一行四坑、焦点轮播、手动换组、入口 + 招商。每类组件只选一种；同类券的数量差异不自动当作混用样式。

## 手机端走查顺序

| 环节 | 操作 | 完成条件与证据 |
| --- | --- | --- |
| S0：确认对象与后台预检 | 填写活动、会场入口、框架、周期/分期、设备；收集主会场参考及后台配置。 | 对象与操作范围明确；配置缺失逐项待确认。 |
| S1：进入并采集首屏 | 打开指定会场，确认标题/主视觉与活动信息，待页面稳定，**未滚动时截图**。 | 目标确认、无遮挡首屏；检查首屏完整 feeds 商品及底部导航。 |
| S2：检查主视觉 | 检查图标、背景衔接、人物数量、LOGO 重叠；商品数量单列建议。 | 保存完整主视觉；字体检查缺模板时待确认。 |
| S3：触发吸顶导航 | 小幅下滑，确认真实吸顶状态后截图，与首屏配对。 | 首屏/吸顶两种状态齐备；不再为该环节继续无目标滚动。 |
| S4：按楼层顺序采集 | 保留截图重叠，记录权益、导购、分类 Tab 和 feeds；采集楼层交界。 | 前置楼层序列完整；核对框架、样式及新增楼层位置。 |
| S5：检查 feeds 与导航 | 采集相邻完整商卡、左右边缘、加购区域和底部导航。 | 检查非白布局；精确值、背景政策、主会场一致性有缺口则待确认。 |
| S6：验证只读跳转 | 仅验证已确认的规则入口和需要跳转的利益点，每次保存落地页后返回。 | 清单逐项有证据或明确待确认；领券、加购等操作另行验证。 |
| S7：归档并停止 | 输出逐项判定、来源、证据和整改建议，分别统计硬性项、建议及缺口。 | 证据齐备后立即停止；未验证项目不能计为通过。 |

原文没有要求完整遍历商品底池，也没有给出滑动次数。执行时应设置重试/滚动上限；达到所需证据条件即停止，上限耗尽则记录未完成。点击“加购”不是验证加购边距所需的步骤。

采集记录至少应包含：会场/活动/分期、设备和 App 版本、规范版本与哈希、环节编号、截图顺序、原始截图尺寸、操作及目标确认记录。涉及模型时记录实际请求及返回模型，不凭配置名称推断实际调用。

## 必须保留的待确认项

1. **feeds 白色政策冲突。** 第 1 页图示为“必须 #FFFFFF”；第 5 页正文为“建议 #FFFFFF”；第 6 页明确描述非白色时的商卡布局。未澄清前 OV-010 为 `uncertain`，不能直接把非白色会场判硬性失败。非白色布局可继续检查，布局符合也不等于背景获准。
2. **24PX 的换算和误差容限。** 原文没有给出设计坐标与手机截图像素的比例。先用后台配置确认或建立经认可的换算，再给出精确结论；不能把 24PX 当作 ADB 截图的 24 个像素。商卡间隔及加购边距不得自行追加数值要求。
3. **外部参考尚未提供。** PDF 提到《新大促官方会场白皮书》《营销会场搭建指引》《官方会场应用规范-主题视觉》，没有可用链接。本次没有引入这些文档的未见内容，字体等依赖项需要后续补齐材料。
4. **后台配置不能由手机外观推断。** 活动标题组件类型、倒计时模板、分期大促模板和底池总量需要后台证据。示例活动、日期、组件 ID 不能当作所有任务的固定参数。

## 与当前项目衔接

`screenshot-inspection.json` 已按现有 `Specification` 数据结构整理，可用于 `scripts/replay_inspection.py --spec ...` 的历史截图回放，也可作为 `inspection` 类型 Skill 的 `specification_json` 提交给现有创建 API。创建 Skill 还需提供名称和 prompt。本次没有修改数据库或创建线上 Skill。

现有 Markdown 上传接口创建的是普通 `analysis` 类型 Skill，不会自动将本目录的完整流程变成手机操作任务。`walkthrough.json` 是供后续执行器接入的流程资产，当前 Worker **没有执行此格式的能力**。

单图检查集只覆盖：本图完整可见的权益样式、导购样式、底部导航可见性、导航图标清晰度、非白背景卡片/加购间隔、头图背景衔接、LOGO 重叠及人物数量。返回的是**局部视觉结论**，不能作为 23 项整体验收通过的依据。参考图供人工审核，当前平台不会自动把 `assets` 中的参考图片附加到模型请求。

完整走查后续需要执行器关联首屏/吸顶截图、楼层序列及后台证据，并独立判断目标已到达、证据已齐备。应先修复此前真机验收发现的 AutoGLM 到页后不停、错误结束仍标完成的问题，再用具体会场验收此流程。

逐项结果使用 `pass / fail / uncertain / not_applicable`。建议偏离单列；有适用硬性项未验证时，整体只能标记部分完成。源文冲突、缺参考或缺配置不能由模型自行补出标准。
